ОТЧЕТ ПО ПРОЕКТУ MODIFICATION ANDROID/MT6580 -> PORTABLE LINUX PC
Дата составления: 02.10.2026

======================================================================
1. ЦЕЛЬ ПРОЕКТА
======================================================================

Основная цель проекта — превратить реальный китайский смартфон на MediaTek MT6580
в максимально самостоятельное портативное ARM Linux-устройство.

Итоговая концепция:
- собственное Linux-ядро;
- собственный Device Tree;
- использование реального boot/kernel/DT/DTBO дампа именно этого телефона;
- постепенный отказ от Android userspace;
- Debian ARMHF как промежуточная и, возможно, базовая Linux-среда;
- графическая оболочка XFCE;
- работа с LCD и touchscreen напрямую через Linux;
- поддержка microSD;
- Wi-Fi/Bluetooth/USB/аудио/датчиков/камер по мере портирования;
- автоматический поворот экрана;
- управление яркостью;
- возможность запуска Linux-приложений;
- потенциальный запуск Windows x86-приложений через Box86/Wine;
- дальнейшая работа над аппаратными возможностями.

ВАЖНЫЙ ПРИНЦИП:
Проект не должен превращаться просто в Debian chroot внутри Android.
Конечная задача — самостоятельная Linux-система с собственным ядром и
минимально необходимым boot/userspace.

2. ИСТОЧНИКИ, КОТОРЫЕ СЧИТАЮТСЯ ДОСТОВЕРНЫМИ
======================================================================

Главный источник:
- реальный телефон;
- live-данные устройства;
- PHONE_DUMP;
- дампы разделов, снятые непосредственно с этого телефона.

НЕ ИСПОЛЬЗОВАТЬ как источник прошивки:
- папку MT6580S24;
- чужие boot.img;
- чужие LK/preloader;
- чужие kernel/vendor images;
- чужие recovery;
- любые неизвестные образы, не принадлежащие этому аппарату.

Причина:
ранее было установлено, что содержимое MT6580S24 относится к другому/чужому
варианту устройства и не должно использоваться для восстановления или
построения нашего boot chain.

Публичные GitHub-репозитории с MT6580 можно использовать только как
справочные материалы для понимания структуры ядра, Device Tree и драйверов.

6. ИССЛЕДОВАНИЕ MULTI-BUFFER / DISPLAY
======================================================================

В процессе экспериментов было установлено, что Android display stack
использует несколько буферов/очередей.

Рассматривались:
- framebuffer;
- BufferQueue;
- gralloc;
- HWC;
- DMA-BUF;
- ION;
- несколько framebuffer/display buffers.

Вопрос "можно ли перенаправить картинку в другой буфер" остаётся актуальным
для дальнейшей оптимизации, но уже понятно, что простая запись в fb0 не
означает полного контроля над физическим LCD, если Android display stack
продолжает использовать тот же display controller.

Следующий уровень решения:
- либо полностью взять display controller под контроль Linux;
- либо корректно отключить Android display stack;
- либо создать отдельный Linux framebuffer/DRM path;
- либо портировать необходимый MediaTek display driver.

13. ИЗВЛЕЧЕНИЕ РЕАЛЬНОГО DTB
======================================================================

В odmdtbo-original.img был найден стандартный FDT magic:

    d0 0d fe ed

Он находится на:
    offset 0x400

Заголовок:

    magic:
        0xd00dfeed

    totalsize:
        0xb15b = 45403 bytes

    off_dt_struct:
        0x38

    off_dt_strings:
        0x9b50

    off_mem_rsvmap:
        0x28

    version:
        0x11 = 17

    last_comp_version:
        0x10

    size_dt_strings:
        0x160b = 5643

    size_dt_struct:
        0x9b18 = 39704

Был извлечён:

    device.dtb

Команда:

    python -c "d=open('odmdtbo-original.img','rb').read(); o=0x400; size=int.from_bytes(d[o+4:o+8],'big'); open('device.dtb','wb').write(d[o:o+size]); print('DTB:',hex(o),'size:',size,'end:',hex(o+size))"

Результат:
    DTB: 0x400
    size: 45403
    end: 0xb55b

Проверка:
    SIZE=45403
    MAGIC=0xd00dfeed
    TOTAL=45403
    VERSION=17

DTB был успешно декомпилирован dtc в:

    device.dts

dtc выдавал предупреждения:
- unit_address_vs_reg
- avoid_default_addr_size
- gpios_property
- interrupts_property
- unique_unit_address
и другие.

Эти предупреждения ожидаемы для overlay/фрагмента и не означают,
что декомпиляция провалилась.

27. ВАЖНЫЕ РИСКИ
======================================================================

1. MT6580 старый и имеет много vendor-specific кода.
2. Linux 3.18.79 сильно отличается от современных mainline kernels.
3. MediaTek display stack сильно завязан на vendor kernel.
4. Mali-400 требует отдельного внимания к userspace/kernel ABI.
5. Android 8.1 использует старый graphics stack.
6. Полная замена Android display stack может вызвать watchdog/reboot.
7. Неверный DT может привести к зависанию или неработоспособности
   периферии.
8. Ошибки в PMIC/GPIO могут быть аппаратно опасными.
9. Нельзя экспериментировать с preloader/LK без оригинальных резервных
   копий.
10. Нельзя прошивать неизвестные DT/boot образы только потому, что они
    относятся к MT6580.

28. БЕЗОПАСНЫЙ РЕЖИМ РАЗРАБОТКИ
======================================================================

Пока работа ведётся в режиме:
    READ / ANALYZE / EXTRACT

Предпочтение:
- читать разделы;
- делать копии;
- извлекать DT;
- анализировать kernel;
- проверять live sysfs/proc;
- строить userspace;
- запускать временные эксперименты.

До появления полностью проверенного собственного boot chain:
- не менять preloader;
- не заменять LK;
- не форматировать критические разделы;
- не стирать NVRAM/NVDATA;
- не прошивать чужой boot;
- не прошивать чужой DT;
- не менять partition layout.

Оригинальные образы должны оставаться резервной точкой восстановления.

32. ИТОГ
======================================================================

На текущем этапе у проекта есть реальная аппаратная база и значительный
объём первичных данных, снятых непосредственно с устройства.

Самое важное достижение — получение и успешный разбор Device Tree overlay
из оригинального odmdtbo. Благодаря этому уже точно установлены ключевые
элементы железа, включая NT35590 AUO LCD и Ilitek touchscreen.

Также доказано, что Linux userspace может получить доступ к физическому
framebuffer телефона и выводить изображение на LCD.

Проект теперь логично переводить из режима экспериментов с Android/chroot
в режим систематического восстановления hardware description и построения
собственного kernel + Device Tree.

Главная ближайшая цель:
    восстановить связи overlay -> base DT,
    построить минимальный собственный DTS,
    затем постепенно переносить периферию в собственный Linux kernel.
